# 📌 SSR (Server-Side Rendering)

> 💡 **서버에서 HTML을 미리 만들어서 보내주는 방식**

## SSR vs CSR 비교

| 구분 | SSR (서버 렌더링) | CSR (클라이언트 렌더링) |
| --- | --- | --- |
| 렌더링 위치 | 서버에서 HTML 생성 | 브라우저에서 JS로 생성 |
| 초기 로딩 | ⚡ 빠름 (완성된 HTML) | 🐢 느림 (빈 HTML → JS 로드) |
| SEO | ✅ 좋음 | ❌ 나쁨 |
| 서버 필요 | 필요 (Node.js 등) | 불필요 (정적 파일만) |
| 호스팅 | EC2, ECS 필요 | S3만으로 가능 |

## 동작 방식

```
[ SSR ]
브라우저 → 서버 (HTML 생성) → 완성된 HTML → 바로 표시! ⚡

[ CSR ]
브라우저 → 서버 → 빈 HTML + JS → JS 실행 → 렌더링 → 표시 🐢
```

> 📝 **Next.js와의 관계**
> - Next.js는 기본적으로 SSR 지원
> - SSR 사용 시 → 서버 필요 → EC2, ECS 등 필요
> - SSR 미사용 (정적 export) 시 → S3만으로 가능

# 🖥️ EC2 (Elastic Compute Cloud)

> 💡 **가상 서버 - AWS에서 빌려 쓰는 컴퓨터**

## 개념도

```
┌─────────────────────────────────┐
│         EC2 인스턴스            │
│  ┌───────────────────────────┐  │
│  │   운영체제 (Ubuntu 등)     │  │
│  │  • 애플리케이션 실행       │  │
│  │  • Docker 실행            │  │
│  │  • 웹서버 (Nginx)         │  │
│  └───────────────────────────┘  │
│   CPU: 2코어 | RAM: 4GB | SSD   │
└─────────────────────────────────┘
```

## 특징

- ✅ 원하는 OS, 사양(CPU, RAM) 선택 가능
- ✅ SSH로 직접 접속해서 관리
- ✅ 24시간 실행되는 서버 필요할 때 사용
- ⚠️ **직접 관리 필요** (업데이트, 보안 패치 등)

## 주요 인스턴스 타입

| 타입 | 사양 | 용도 | 월 비용 (서울) |
| --- | --- | --- | --- |
| t3.micro | 2vCPU, 1GB | 테스트/개발 | ~$10 |
| t3.small | 2vCPU, 2GB | 소규모 서비스 | ~$20 |
| t3.medium | 2vCPU, 4GB | 중소규모 | ~$40 |
| t3.large | 2vCPU, 8GB | 중규모 | ~$80 |

> 🎯 **비유**: 렌탈 컴퓨터

# 🐳 ECS (Elastic Container Service)

> 💡 **컨테이너 관리 서비스 - Docker 컨테이너를 쉽게 실행/관리**

## 개념도

```
┌─────────────── ECS 클러스터 ───────────────┐
│                                            │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│  │ Service  │  │ Service  │  │ Service  │ │
│  │(Frontend)│  │(Backend) │  │ (Worker) │ │
│  ├──────────┤  ├──────────┤  ├──────────┤ │
│  │Task Task │  │Task Task │  │  Task    │ │
│  │ 🐳  🐳   │  │ 🐳  🐳   │  │   🐳     │ │
│  └──────────┘  └──────────┘  └──────────┘ │
│                                            │
└────────────────────────────────────────────┘
```

## 핵심 구성 요소

| 구성 요소 | 설명 | 비유 |
| --- | --- | --- |
| **Cluster** | ECS 리소스의 논리적 그룹 | 🏭 공장 |
| **Service** | 지정된 수의 Task를 유지/관리 | �icing 생산 라인 |
| **Task** | 실행 중인 컨테이너 인스턴스 | 📦 제품 |
| **Task Definition** | 컨테이너 설정 (이미지, CPU, 메모리 등) | 📋 설계도 |

## ECS vs 직접 Docker 실행

| 구분 | EC2에서 직접 Docker | ECS |
| --- | --- | --- |
| 컨테이너 관리 | 수동 | 자동 |
| 장애 복구 | 직접 처리 | 자동 재시작 |
| 스케일링 | 수동 | Auto Scaling |
| 로드밸런싱 | 직접 설정 | ALB 통합 |
| 배포 | 수동 | Rolling 배포 |

> 🎯 **비유**: 컨테이너 관리자

# ⚡ Fargate

> 💡 **서버리스 컨테이너 - 서버 관리 없이 컨테이너만 실행**

## EC2 vs Fargate 비교

```
[ EC2 방식 ]
┌──────────────────────────────────────┐
│              EC2 인스턴스             │  ← 직접 관리 필요 😓
│  ┌────────┐ ┌────────┐ ┌────────┐   │
│  │컨테이너│ │컨테이너│ │컨테이너│   │
│  └────────┘ └────────┘ └────────┘   │
└──────────────────────────────────────┘

[ Fargate 방식 ]
  ┌────────┐ ┌────────┐ ┌────────┐
  │컨테이너│ │컨테이너│ │컨테이너│      ← 컨테이너만 관리 😊
  └────────┘ └────────┘ └────────┘
      ☁️          ☁️          ☁️
   (서버는 AWS가 알아서!)
```

## ECS 실행 유형 비교

| 구분 | ECS + EC2 | ECS + Fargate |
| --- | --- | --- |
| 서버 관리 | 직접 (EC2 관리) | 없음 (AWS 관리) |
| 가격 | 💰 저렴 | 💰💰 비쌈 |
| 스케일링 | EC2 먼저 늘려야 함 | 즉시 컨테이너 추가 |
| 시작 시간 | ⚡ 빠름 | 🕐 약간 느림 (30초~1분) |
| 적합한 경우 | 예측 가능한 워크로드 | 가변적 워크로드 |

## Fargate 비용 예시 (서울 리전)

| 사양 | 시간당 | 월 비용 (24/7) |
| --- | --- | --- |
| 0.25 vCPU + 0.5GB | ~$0.012 | ~$9 |
| 0.5 vCPU + 1GB | ~$0.025 | ~$18 |
| 1 vCPU + 2GB | ~$0.050 | ~$36 |
| 2 vCPU + 4GB | ~$0.100 | ~$72 |

> 🎯 **비유**: 서버 없는 컨테이너 실행

# 📦 S3 (Simple Storage Service)

> 💡 **파일 저장소 - 무한 용량의 클라우드 스토리지**

## 개념도

```
┌─────────────────────────────────────┐
│        S3 버킷 (Bucket)              │
│  📁 images/                         │
│     ├── logo.png                    │
│     └── banner.jpg                  │
│  📁 static/                         │
│     ├── index.html                  │
│     └── style.css                   │
│  📁 uploads/                        │
│     └── user-files/                 │
└─────────────────────────────────────┘
```

## 주요 용도

| 용도 | 설명 |
| --- | --- |
| 정적 파일 호스팅 | HTML, CSS, JS, 이미지 |
| 정적 웹사이트 | CSR 앱 배포 (React, Vue 등) |
| 파일 업로드 저장 | 사용자 업로드 파일 |
| 백업/아카이브 | 데이터 백업 |
| 로그 저장 | 애플리케이션 로그 |

## 특징

- ✅ 용량 무제한
- ✅ 99.999999999% 내구성 (데이터 손실 거의 없음)
- ✅ 쓴 만큼만 과금 (~$0.025/GB/월)

> 🎯 **비유**: 무한 클라우드 USB

# 🌐 CloudFront (CDN)

> 💡 **콘텐츠 전송 네트워크 - 전세계에서 빠르게 콘텐츠 제공**

## 개념도

```
                    ┌─── 서울 엣지 ←── 🇰🇷 한국 사용자
                    │
원본 서버 (S3) ────┼─── 도쿄 엣지 ←── 🇯🇵 일본 사용자
                    │
                    └─── 미국 엣지 ←── 🇺🇸 미국 사용자
```

## 동작 방식

```
1️⃣ 첫 번째 요청 (캐시 없음)
   사용자 → 엣지 → 원본 서버 → 엣지에 캐시 저장 → 사용자

2️⃣ 두 번째 요청 (캐시 있음)
   사용자 → 엣지 → (캐시에서 바로 응답) → 사용자  ⚡ 빠름!
```

## 주요 기능

| 기능 | 설명 |
| --- | --- |
| 🌍 글로벌 캐싱 | 전세계 400+ 엣지 로케이션 |
| 🔒 HTTPS | 무료 SSL 인증서 제공 |
| 🛡️ DDoS 방어 | AWS Shield 기본 통합 |
| 📦 압축 | Gzip/Brotli 자동 압축 |

> 🎯 **비유**: 전세계 편의점 체인

# 🔒 VPC (Virtual Private Cloud)

> 💡 **가상 사설 네트워크 - AWS 내 나만의 격리된 네트워크**

## 개념도

```
┌───────────────────── VPC ─────────────────────┐
│                                                │
│   ┌─── Public Subnet ────┐                    │
│   │  • ALB               │ ← 인터넷 접근 O    │
│   │  • NAT Gateway       │                    │
│   └──────────────────────┘                    │
│              │                                 │
│   ┌─── Private Subnet ───┐                    │
│   │  • EC2 (앱 서버)      │ ← 인터넷 접근 X    │
│   │  • ECS (컨테이너)     │   (외부 차단)      │
│   │  • RDS (데이터베이스) │                    │
│   └──────────────────────┘                    │
│                                                │
└────────────────────────────────────────────────┘
```

## 핵심 구성 요소

| 구성 요소 | 설명 | 용도 |
| --- | --- | --- |
| **Subnet** | VPC 내 IP 범위 분할 | 리소스 배치 영역 |
| **Public Subnet** | 인터넷 직접 통신 가능 | ALB, NAT, Bastion |
| **Private Subnet** | 인터넷 직접 불가 | EC2, ECS, RDS |
| **Internet Gateway** | VPC ↔ 인터넷 연결 | Public 서브넷 통신 |
| **Security Group** | 인스턴스 방화벽 | 포트/IP 허용/차단 |

## 왜 나누는가?

> ⚠️ **DB가 인터넷에 직접 노출되면 해킹 위험!**
>
> → Private에 두고 ALB를 통해서만 접근하게 함

> 🎯 **비유**: 회사 사설망

# ⚖️ ALB (Application Load Balancer)

> 💡 **애플리케이션 로드밸런서 - 트래픽을 여러 서버에 분산**

## 개념도

```
              사용자 요청
                  │
                  ▼
           ┌─────────────┐
           │     ALB     │
           └──────┬──────┘
                  │
      ┌───────────┼───────────┐
      │           │           │
      ▼           ▼           ▼
 ┌─────────┐ ┌─────────┐ ┌─────────┐
 │  EC2-1  │ │  EC2-2  │ │  EC2-3  │
 │  (33%)  │ │  (33%)  │ │  (33%)  │
 └─────────┘ └─────────┘ └─────────┘
```

## 주요 기능

| 기능 | 설명 |
| --- | --- |
| ⚖️ 로드밸런싱 | 여러 서버에 트래픽 분산 |
| ❤️ 헬스체크 | 서버 상태 확인, 장애 시 제외 |
| 🔒 HTTPS 처리 | SSL 인증서 관리 |
| 🛤️ 경로 기반 라우팅 | `/api/*` → 백엔드, `/*` → 프론트 |

## 경로 기반 라우팅 예시

```
ALB
 │
 ├── /api/* ──────▶ Backend (ECS Tasks)
 │
 └── /* ──────────▶ Frontend (ECS Tasks)
```

> 🎯 **비유**: 교통 경찰

# 🗄️ RDS (Relational Database Service)

> 💡 **관리형 데이터베이스 - AWS가 관리해주는 DB 서비스**

## 개념도

```
┌─────────────────────────────────────────────┐
│                    RDS                       │
│  ┌───────────────────────────────────────┐  │
│  │         PostgreSQL / MySQL            │  │
│  │                                       │  │
│  │  ✅ 자동 백업 (매일)                   │  │
│  │  ✅ 자동 패치 (보안 업데이트)          │  │
│  │  ✅ Multi-AZ (이중화)                 │  │
│  │  ✅ 모니터링 (CloudWatch)             │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

## EC2에 직접 설치 vs RDS

| 구분 | EC2에 직접 DB 설치 | RDS |
| --- | --- | --- |
| 설치/설정 | 직접 😓 | 클릭 몇 번 😊 |
| 백업 | 직접 스크립트 작성 | 자동 |
| 업데이트 | 직접 | 자동 |
| 이중화 | 복잡한 설정 | 클릭 한 번 |
| 비용 | 💰 저렴 | 💰💰 비쌈 (관리비 포함) |

## Multi-AZ (고가용성)

```
┌─ 가용 영역 A ─┐     ┌─ 가용 영역 B ─┐
│               │     │               │
│  Primary DB  │────▶│  Standby DB  │
│     (메인)    │동기화│    (대기)     │
│               │     │               │
└───────────────┘     └───────────────┘
        │                     │
        └── 장애 시 자동 전환 ──┘
```

> 🎯 **비유**: DB 풀케어 서비스

# 🚪 NAT Gateway

> 💡 **NAT 게이트웨이 - Private 서브넷의 인터넷 출구**

## 필요한 이유

> Private 서브넷의 EC2가 해야 할 일:
> - `npm install` (패키지 다운로드)
> - `apt update` (시스템 업데이트)
> - 외부 API 호출 (결제 API, 소셜 로그인 등)
>
> → 인터넷 **나가는** 통신이 필요!
> → 하지만 외부에서 **들어오는** 건 차단해야 함

## 동작 방식

```
    인터넷
       ▲
       │ (나가기만 가능 ✅, 들어오기 ❌)
       │
┌──────┴───────┐
│ NAT Gateway  │  ← Public Subnet
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ Private EC2  │  ← Private Subnet
│              │
│ npm install ─┼──▶ NAT를 통해 인터넷으로
└──────────────┘
```

## 비용

| 항목 | 비용 |
| --- | --- |
| 시간당 | ~$0.059 (서울) |
| 월 (24/7) | ~$45 |
| 데이터 처리 | $0.059/GB |

> 💡 **비용 절감 팁**: 개발 환경에서는 NAT Instance(EC2)로 대체 가능 (~$5/월)

> 🎯 **비유**: 회사 프록시 서버

# 📬 SQS (Simple Queue Service)

> 💡 **메시지 대기열 - 비동기 작업 처리를 위한 큐**

## 개념도

```
┌───────────┐     ┌─────────────────┐     ┌───────────┐
│           │     │      SQS        │     │           │
│ Producer  │────▶│ [ 4 | 3 | 2 | 1 ] ────▶│ Consumer  │
│ (API서버) │     │   메시지 대기열  │     │ (Worker)  │
│           │     │                 │     │           │
└───────────┘     └─────────────────┘     └───────────┘
      │                                         │
      └── 메시지 넣고 즉시 응답          순차적으로 처리 ──┘
```

## 사용 예시

### 📧 이메일 발송

```
API 요청 → "이메일 발송" 메시지 → SQS → 즉시 응답
                                   ↓
                        Worker가 이메일 발송
```

### 🖼️ 이미지 처리

```
이미지 업로드 → "썸네일 생성" 메시지 → SQS → 즉시 응답
                                       ↓
                            Worker가 썸네일 생성
```

### 🤖 AI 요청 처리

```
AI 요청 → "AI 분석" 메시지 → SQS → 즉시 응답
                              ↓
                   Worker가 AI API 호출
```

## 장점

| 장점 | 설명 |
| --- | --- |
| ⏱️ 비동기 처리 | 오래 걸리는 작업을 백그라운드로 |
| ⚖️ 부하 분산 | 트래픽 급증 시 큐에 쌓아두고 천천히 처리 |
| 🛡️ 장애 격리 | Worker 죽어도 메시지 유실 없음 |
| 🔄 재처리 | 실패한 메시지 자동 재시도 |

> 🎯 **비유**: 대기표 시스템
